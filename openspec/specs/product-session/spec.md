# 本机产品会话

## Purpose

为产品提供可在本机验证的 Host／Client 会话及本轮手动原成员恢复，明确本地与远端玩家的共用裁决、成员状态、消息与运行生命周期。厨房玩法由相关独立规格定义；本规格不宣称持久进度、正式传输选型、自动重连或跨进程重启恢复已经支持。

本规格保留交接 A3／G3 的 Match／Participant 与连接分离，断线保留离线成员，并接入本 Match 内存凭证支持手动恢复原成员；该凭证不持久化，不以普通 Join 的新连接成立冒充旧身份恢复。Profile、跨设备身份和 Host 迁移尚未纳入本原型。

## Requirements

### Requirement: 产品会话所有者与角色分离

产品会话 MUST 通过 ET Child／Component 关系持有本轮状态、入口及下级资源。Host 同时包含权威会话和本地客户端，Solo 包含相同权威会话和本地客户端但不创建网络监听，远端 Client 仅包含客户端；运行角色不得由主线／稳定工作区职责决定。成员权威和客户端投影须分开，不共享可变业务状态。正式 Host 与 Solo 须持有同一持续厨房与当前关卡合同，远端不得创建本端餐厅权威。

#### Scenario: 启动 Host
- **WHEN** 合法 Host 配置进入产品入口
- **THEN** 创建本轮权威会话及本地客户端，本地玩家必须获得真实加入确认，不能仅因拥有 Host 而报告已加入；正式餐厅由本轮权威持有且只有一个业务驱动

#### Scenario: 启动远端 Client
- **WHEN** 合法 Client 配置进入产品入口
- **THEN** 仅创建本端客户端，通过指定目标加入，不创建本端成员权威或使用 Demo 账号服务

#### Scenario: 启动 Solo
- **WHEN** 合法 Solo 配置进入产品入口
- **THEN** 创建本地权威及独立客户端，完成真实本地加入，不创建网络监听或对自身 UDP 连接，不报告网络监听就绪

### Requirement: 逻辑成员独立于连接

Match MUST 独立持有 Participant 和名单权威，HostPeer／Session 只绑定成员，不作为其释放父对象。连接断开仅撤销绑定并标离线，显式 Leave 才退出逻辑协作；合法恢复必须持有本 Match 内有效恢复凭证，不准凭自报编号接管旧成员。首版恢复仅限 Host 与 Client 进程均保留的本轮运行。

#### Scenario: 断线释放连接子树
- **WHEN** 某已加入 Session 及其 HostPeer 被清理
- **THEN** 原 Participant 由 Match 保留，在线状态变为离线，其他成员及公共消息资源不受影响

#### Scenario: 新连接自报旧成员编号
- **WHEN** 新绑定试图只用请求自报的旧 MemberId 恢复身份
- **THEN** 不授予原成员权限；仅合法新加入或持有效凭证的恢复请求可取得相应权限

### Requirement: 本地与远端共用裁决

Host 本地玩家 MUST 使用进程内消息发送与接收，不向自己发送 UDP。远端入口只处理传输、可信身份绑定和转交；两种路径的加入、主动退出及最小命令须进入同一套权威处理，不因本地身份绕过验证。成员状态的修改须统一有序提交。

#### Scenario: 两种路径执行同一请求
- **WHEN** 已加入的本地玩家与远端玩家提交同一种无玩法探测请求
- **THEN** 进入相同权威处理，分别得到自己的成员编号及请求数据，答复不会互相匹配

#### Scenario: 请求自报他方身份
- **WHEN** 请求试图指定另一个成员或内部 Actor 地址
- **THEN** 入口使用实际绑定身份裁决，伪造内容不能替换成员或直达内部处理

### Requirement: 加入确认与协议兼容

系统 MUST 区分连接建立与加入成功；只有取得当前 Match 的成功答复、本人成员编号和有效名单后，客户端才进入已加入。加入须核对明确协议版本，提交前失败不留成员，提交后答复丢失保留 Match 所属离线成员；不得自动重试、更新稳定基线或回落 Demo。

#### Scenario: 连接建立但尚无答复
- **WHEN** 连接已经建立，加入确认尚未到达
- **THEN** 客户端保持加入中，不发布加入成功，不允许发送已加入成员命令

#### Scenario: 协议不兼容或加入失败
- **WHEN** 本端与 Host 协议版本不兼容，或当前请求加入失败
- **THEN** 返回明确失败并收尾本请求资源，不报告成功、不自动更新另一端

#### Scenario: 同一绑定重复加入
- **WHEN** 已加入绑定再次请求加入
- **THEN** 不新增第二个成员，返回既有加入结果或明确重复错误

#### Scenario: 等待加入期间退出
- **WHEN** 客户端在加入确认前退出
- **THEN** 旧答复不能把客户端改为已加入；未提交登记不创建成员，已经提交的成员离线且由 Match 持有，不因取消等待删除逻辑身份

#### Scenario: 加入已提交但答复未送达
- **WHEN** Host 已提交成员登记，随后连接断开导致确认无法送达
- **THEN** Host 保留同一成员并标离线，Client 不宣告 Joined，不自动重试或删除该逻辑身份

### Requirement: 名单快照与本轮隔离

Host MUST 唯一维护 Match 的逻辑成员名单及在线／离线状态，每次实际变更生成递增版本完整快照。客户端只应用所属 Match 且不旧于当前版本的数据；来自其他 Match 或失效实例的数据不得应用。投影独立，HostSession 不建立第二份可写名单。

#### Scenario: 两端加入后的名单
- **WHEN** 本地玩家与远端玩家完成加入并收到当前名单
- **THEN** 各端对同一版本观察到相同成员，客户端数据不引用 Host 可变成员实体或容器

#### Scenario: 旧快照迟到
- **WHEN** 较旧名单快照或上一轮会话数据迟到
- **THEN** 不回退当前名单版本，不写入另一轮客户端状态

#### Scenario: 通知早于加入答复
- **WHEN** 名单通知在本人加入确认前到达
- **THEN** 可以暂存当前会话数据，但不提前宣告加入；后续加入答复中的旧版本也不能覆盖较新名单

#### Scenario: 尚未确认 Match 的通知
- **WHEN** 正在 Joining 的 Client 收到完整名单，尚未确认其 MatchId
- **THEN** 仅在当前入口下保留候选数据，待本人 Join 确认匹配 MatchId 后才安装，其他 Match 的通知不能设定当前身份

#### Scenario: 相同业务编号的旧绑定回复
- **WHEN** 旧入口回复或通知在本端下一轮接入后到达
- **THEN** 先核对本轮实例和绑定身份，不能仅因 MatchId 或 MemberId 相似就应用到新绑定

### Requirement: 协议入口白名单与参数校验

产品入口 MUST 核对协议版本、合法消息类型、当前 Match、必需字段与明确载荷限制，拒绝未知或内部消息。身份来自可信接入绑定，不来自请求自报成员、Actor 地址或机器身份。心跳只维护连接，不增加成员或成为世界时钟。餐厅各动作族须按明确交付范围逐项开放并进入共同裁决；新增制作与控制入口不能放开内部转交消息、未知动作或越过共享控制权限。

#### Scenario: wire 发送内部转交消息
- **WHEN** 远端构造仅供进程内共同裁决的消息类型
- **THEN** 入口拒绝转交，不授予内部身份，也不修改 Match

#### Scenario: 无效探测载荷
- **WHEN** Probe 使用错误 Match、缺失必需字段或超出明确载荷限制
- **THEN** 返回明确拒绝，不回落 Demo，不创建成员或修改名单

#### Scenario: 核心餐厅请求通过可信入口
- **WHEN** 同版远端提交已开放的合法两菜动作、无权限控制或尚未开放的动作
- **THEN** 合法个人动作进入共同裁决；后两类明确拒绝，不能靠动作数值范围或自报身份获得权限

### Requirement: 消息与结果所有权

请求、答复和通知 MUST 具有明确释放者，转交须保留各段独立答复关联，不能由内部调用改写原网络请求编号。多人通知不得共享会被接收者回收的同一消息对象，客户端须在回收消息前取得独立状态数据。成功、业务失败、超时和退出须明确区分。

#### Scenario: 网络请求转交本地处理
- **WHEN** 远端请求经过进程内 RPC 后返回
- **THEN** 远端收到匹配原网络请求的答复，内部编号只用于内部等待，不建立另一份私有回调表

#### Scenario: 消息回收后读取投影
- **WHEN** 已处理的消息对象被回收或复用
- **THEN** 客户端成员名单和已接收结果保持有效，其他接收者不读取被回收消息

### Requirement: 状态事件与启动结果

业务 MUST 先提交所属状态再发布观察事件；事件不替代跨进程消息、请求答复或必须成功的初始化步骤。根启动、监听可用和成员加入各有明确结果，记录处理器异常或发布完成本身不能证明产品就绪。产品功能间的后继执行 MUST 由明确消息请求进入裁决；本地观察事件仅呈现已安装状态，不能直接提交后继功能。

#### Scenario: 初始化失败
- **WHEN** 必需初始化步骤失败，但某个事件发布已经返回
- **THEN** 保留真实失败，不进入已加入或报告 Host 完全就绪

#### Scenario: 成员状态通知
- **WHEN** 发布加入或名单变化事件
- **THEN** 观察者读取已经提交的所属客户端或 Host 状态，不能通过事件形成第二份权威

#### Scenario: 事件观察者处理名单变化
- **WHEN** 已提交名单触发本端观察事件
- **THEN** 观察者只读取当前版本，不再次提交同一变更，不增加名单版本，也不触发另一产品角色的初始化

#### Scenario: 收到一次加工完成消息
- **WHEN** 客户端安装已提交快照并收到对应完成消息
- **THEN** 表现观察者可以刷新成品显示，但不再次生成成品；任何后继业务通过其独立请求接入

### Requirement: 监听与连接存活

原型 SHALL 仅连接本机 loopback。Host 监听必须报告实际绑定的非零 endpoint，端口冲突明确失败；不将配置端口 0 或 Pipeline 工具端口交给 Client。远端加入成功后须解除接入验证超时并维持有界心跳及既有空闲断线检查，本地消息通道无需网络心跳。

#### Scenario: 动态监听端口
- **WHEN** Host 配置以端口 0 启动
- **THEN** 报告实际绑定地址和非零端口，另一端显式使用该结果；不猜测或扫描替代端口

#### Scenario: 连接保持空闲
- **WHEN** 已加入的远端连接没有业务命令但双方正常运行
- **THEN** 心跳使连接正常保持；对端失联时有限时间内结束等待并报告失联，不无限积累请求

### Requirement: 单成员与整体退出边界

已提交显式 Leave SHALL 移除当前 Participant 及绑定，重复退出不重复变更名单。意外断线 MUST 立即使入口失效、结束该 Session 网络等待并将成员离线；本地在途请求经拒绝或既有有限超时结束，不承诺单请求即时取消。Leave 未提交的本端关闭按断线处理。整体退出解散 Match，先拒绝新工作再结束本轮等待与资源；单连接退出不停止共用发送器。

#### Scenario: 单个成员主动退出
- **WHEN** 已加入 Client 的显式 Leave 已提交并随后重复清理
- **THEN** 该成员只被移除一次，其他成员继续通信，共用发送器仍可用

#### Scenario: 远端连接意外断开
- **WHEN** 已绑定的远端 Session 退出
- **THEN** 旧绑定失去命令资格，网络等待结束、本地在途请求按约定收尾，逻辑成员离线保留；重复清理不增加名单版本，不自动重连

#### Scenario: 关闭时仍有已排队请求
- **WHEN** 一个连接关闭，仍有其已接入的本地请求等待共同裁决
- **THEN** 请求在提交前重新核对入口并明确拒绝，处理入口保留到在途收尾；其他玩家继续通信，不停止公共发送器来取消单成员请求

#### Scenario: 动作提交后发生断线
- **WHEN** 合法 Join 或 Leave 已经提交，随后原连接失效
- **THEN** 保留已提交事实，不将丢失答复当成未执行，不向新连接交付旧答复

#### Scenario: Host 本地玩家单独退出
- **WHEN** Host 本地 Client 的 Leave 已提交，而 Host 根未停止
- **THEN** 只结束该本地成员和接入，Host 监听及其他成员继续工作，不自动重新加入本地玩家

#### Scenario: Leave 尚未提交时关闭
- **WHEN** Client 发出 Leave 后立即关闭，Host 尚未合法提交该请求
- **THEN** 不宣称成员已经离开，旧入口命令被拒绝并将成员离线保留

#### Scenario: Host 整体退出
- **WHEN** Host 本轮运行结束或启动中失败
- **THEN** 拒绝新加入和命令，结清本轮本地／网络等待并清理已创建资源，旧异步结果不写入下一轮，不释放其他工程资源

### Requirement: 固定 Tick 玩法权威与共同命令

地图玩法 MUST 由 Host 的固定业务 Tick 唯一修改世界事实。本地、Solo 和远端玩家使用相同命令及执行验证；传输入口、UI、动画、心跳和客户端插值均不得写入权威位置或物品。成员控制保持既有有序处理，玩法入口只快速接收意图，不等待完整行走才能处理其他请求。

#### Scenario: 三种入口执行相同玩法
- **WHEN** Solo、本地 Host 玩家和远端玩家在相同地图条件下提交同一动作
- **THEN** 使用同一业务验证与 Tick 提交规则，不存在单机直接改物品或本地绕过停驻检查的捷径

#### Scenario: 自动行走仍在进行
- **WHEN** 某成员正在自动接近台面，同时另一成员请求操作或退出
- **THEN** 其他请求继续被处理，不被前一成员等待到达的请求占住公共入口

### Requirement: 接收结果与最终结果分离

系统 MUST 区分传输入口拒绝、意图已接收、动作最终成功、业务拒绝和被替换／退出取消。每条意图具有所属世界与绑定的业务编号，不以网络 RPC 编号作为动作身份；重复提交同一编号不得重复执行。调用超时不等于动作未执行，不自动重试或把旧结果交给新绑定。

行走或目的格满员等待期间 MUST 保持进行中；安装目的地不等于动作完成。只有 Host 已提交到达目的格才能报告行走成功，被新目标替换的旧行走须报告取消。

#### Scenario: 台面动作已接收但尚未到达
- **WHEN** Host 已接收自动接近意图，角色尚未走到操作格
- **THEN** 客户端只显示进行中；只有最终提交成功才显示物品转移完成

#### Scenario: 重复命令与迟到结果
- **WHEN** 同一业务编号重复进入，或旧绑定动作结果在新一轮到达
- **THEN** 重复命令不再转移物品，旧轮结果不改变当前投影或当前动作状态

#### Scenario: 行走、等待与改目标的结果
- **WHEN** 行走命令已经接收，但角色尚未到达目的格或仍在等待空位
- **THEN** 保持进行中，到达后才报告一次成功；若改去新目标，原行走报告取消，新目标继续保持独立结果

### Requirement: 独立地图投影与就绪边界

Host SHALL 发布包含世界身份、版本和 Tick 的地图快照；各端复制为独立只读投影，拒绝旧版本、错误世界及失效绑定数据。成功 Join 只证明成员加入；地图可操作还要求取得匹配世界的地图、本人角色及必要视图。通知先于 Join 时不能自行确立本人身份。

#### Scenario: 初次加入与地图初始化
- **WHEN** Client 收到成功 Join，但地图快照或本人角色尚未可用
- **THEN** 保持地图初始化状态，不允许缺少世界身份的操作；匹配数据和视图就绪后才开启地图输入

#### Scenario: 旧快照或池化消息回收
- **WHEN** 旧世界快照迟到，或当前快照消息被回收
- **THEN** 旧数据不能覆盖当前世界，已安装投影仍保持有效且不引用回收消息或 Host 实体

### Requirement: 地图角色与成员退出分离

地图角色 MUST 引用逻辑成员而不由连接持有。单成员断线保留离线成员、移除角色并保留其手持物；已提交 Leave 移除成员并采用同样物品保留收尾。旧绑定未提交玩法失效，其他成员和共用资源继续运行。整体退出停止 Tick、结束本轮意图并释放临时地图，不形成存档或下一轮残留。

#### Scenario: 单成员退出仍可继续交接
- **WHEN** 一名成员断线或已提交 Leave
- **THEN** 其场上角色不再参与行走，手持物可按同格规则拾取；其他成员继续操作，同一角色重复收尾不重复落物

#### Scenario: 地图整轮结束
- **WHEN** Host 停止本轮运行，同时有等待到达的动作和视图加载
- **THEN** 本轮 Tick 与动作结束，晚到结果不修改下一轮；临时地图被释放，不保存持久餐厅进度

### Requirement: 产品命令上下文与类型明确

新增单机产品命令 MUST 携带所属运行世界、适用关卡、绑定代次和正业务编号，并用明确动作及目标身份表达意图。入口根据真实绑定确定发送者，不接受请求自报内部地址或成员身份。关卡建立前的既有格子命令保持原上下文；关卡建立后，新关命令不得省略关卡身份。

#### Scenario: 旧关与伪造身份请求
- **WHEN** 请求属于上一关、失效绑定，或试图使用另一发送者的内部身份
- **THEN** 明确拒绝，不修改当前物品、布局、订单或关卡状态

### Requirement: 最新命令重放与有限结果保留

同一绑定各新增动作族 MUST 共享单调递增的业务编号。最新已接收编号与相同完整载荷重放时返回当前接收／最终事实，不再次执行；同编号不同动作或目标须拒绝，更早编号返回已过期，不保存无限历史或自动重试。业务编号不得用 RPC 编号替代。

#### Scenario: 最新请求重复与编号冲突
- **WHEN** 最新请求重复到达，随后同编号被用于另一目标
- **THEN** 重复返回原接收或最终结果，冲突明确拒绝，世界效果仍只有一次

#### Scenario: 历史结果已不保留
- **WHEN** 较新请求已接收，调用者重放更早编号
- **THEN** 返回已过期且不执行，不把缺少历史结果解释成可以再做一次

### Requirement: 接收动作和工作完成分离

入口 MUST 快速返回接受或拒绝，最终业务结果在共同 Tick 验证提交后产生。接受、到达、成功启动、加工完成及取消属于不同可观察事实；公共入口不得等待整段行走、加工或营业时间。已经接受的动作 MUST 通过明确的终态消息报告成功、业务拒绝或取消结果；长作业须另外报告其实际开始与结束，不能仅靠快照变化推断完成。单次同步业务的响应可以承担其终点。

#### Scenario: 加工请求已经接受
- **WHEN** 请求得到接收回执但角色尚未到位或加工尚未到点
- **THEN** 显示对应进行中事实，不提前报告物品已转移或加工已完成，其他请求仍可处理

#### Scenario: 烘烤开始与真正烤好
- **WHEN** 开始烘烤命令已执行，而烘烤尚有剩余业务时间
- **THEN** 开始成功与作业开始可分别辨认；仅在真实成品提交后产生该作业完成消息，接收回执不代替完成

#### Scenario: 两条动作先后提交
- **WHEN** 同一玩家较新的动作已经接收，较早动作随后完成或被替换取消
- **THEN** 两条动作分别产生带自己身份的终态消息，不因快照只保留最近命令就丢失较早动作出口，旧结果也不覆盖新动作反馈

### Requirement: 取消业务等待保留原调用收尾

调用者退出 MUST 及时结束其业务等待，同时让原物理本地调用由答复、既有有限超时或整体停止收尾。产品入口在途保护须持续到该原调用结束；取消不能提前释放仍承接原消息的入口、重复回收消息或停止公共发送器。原调用结束后的迟到结果不得写入新调用者。

#### Scenario: 界面退出而答复尚未到达
- **WHEN** 界面关闭取消对外等待，原本地请求仍在队列或等待答复
- **THEN** 界面等待为取消，原入口按在途责任保留到收尾，另一调用者仍可正常通信，晚到响应只被收尾

### Requirement: 单机真实消息测试入口

单机功能测试 MUST 能创建隔离产品运行与本地客户端，经真实请求、队列、接收 handler 和业务 Tick 观察结果。测试须分别控制消息投递和业务时间，清理自身运行，拒绝占用正在运行的产品；不能以直接调用 handler 或修改最终状态冒充消息与完整输入验收。

#### Scenario: 控制收到请求与执行时点
- **WHEN** 测试泵入真实本地请求但尚未推进业务 Tick
- **THEN** 可观察接收回执而世界尚未提交，推进 Tick 后才取得动作结果，测试结束无所属运行残留

### Requirement: 单机餐厅模式的关卡隔离

正式单机餐厅模式 MUST 在持续世界身份之外校验当前 Level 身份与代次；角色只属于当前关，结束角色前按唯一位置规则保留手持实物。关卡切换后旧动作和旧投影不得写入新关，厨房的未变实例、内容与剩余份数不得因关卡代次变化重建。本要求不把旧临时样机声明成持久餐厅。

#### Scenario: 世界相同而关卡已经更换
- **WHEN** 同一家餐厅换关后收到上一关的动作或快照
- **THEN** 按关卡身份拒绝，不因世界仍相同便应用旧得分、认领或动作

### Requirement: 单机餐厅沿用本地裁决入口

单机餐厅 MUST 使用既有产品本地加入、独立客户端及共同裁决入口，不创建网络监听。关卡控制、布局、前厅与 buff 请求须遵守相同绑定、上下文、接收／最终结果和消息所有权规则；控制消息泵在暂停期间仍运行，不能让暂停造成无法恢复。

#### Scenario: 暂停后经本地消息恢复
- **WHEN** 本关已暂停，玩家从有效本地客户端请求恢复
- **THEN** 请求经过真实本地入口并取得结果，无需网络、自报内部地址或直接修改 Host 状态

### Requirement: 产品功能的完整消息边界

当前产品的会话、移动实物、加工、顾客订单、前厅工作、清理供应、关卡、布局、Buff、装修和已有单机存档功能 MUST 具有明确消息入口与结果出口；玩家、伙伴、业务时钟和其他功能均遵守此边界。功能内部纯计算及原子效果可以直接调用；框架建树、强制拆树、UI／资源生命周期和旧示例不适用本要求。已有消息入口须复用，不产生平行执行路径。

#### Scenario: 同一功能来自不同触发者
- **WHEN** 玩家或自动调度发起适用于自身身份的同类前厅工作
- **THEN** 均通过明确消息进入同一工作规则，自动来源不能直接完成工作或绕过认领校验

#### Scenario: 确认清理和布局命令结果
- **WHEN** 清理、布局或 Buff 请求被接受后在业务步执行或拒绝
- **THEN** 每条命令产生明确对应结果，消费者无需只观察最近结果字段猜测是否执行

#### Scenario: 查询已有存档
- **WHEN** 用户通过现有选档功能请求浏览或读取一项记录
- **THEN** 请求和成功／失败答复经过本地消息，未合法选定记录不会因此创建运行世界

### Requirement: 自动转换与后继功能经消息裁决

业务时钟到点或上一功能完成时，系统 MUST 发出明确转换／后继请求，再由原领域 owner 在允许的业务步校验并提交。一次阶段转换不得重复执行。跨功能衔接允许经过后续消息轮次；不改变配置时长、暂停规则或单个功能原子效果，不为保持同 Tick 而直接重入执行。必要初始化尚未完成时不得报告业务就绪。

#### Scenario: 加工到点但消息尚未投递
- **WHEN** 烘烤达到所需时间，但其完成转换请求尚未进入裁决
- **THEN** 不提前创建成品，不重复发起同一转换；投递并在允许业务步提交后只创建一份成品并发完成消息

#### Scenario: 清桌完成后安排洗碗
- **WHEN** 清桌完成消息已发出，但洗碗请求尚未提交
- **THEN** 原餐具和待衔接事实仍有明确 owner；投递后只创建一次洗碗工作，直接方法或观察事件不另开第二份

#### Scenario: 暂停时转换等待处理
- **WHEN** 自动加工完成转换仍待处理，此时暂停命令先被提交
- **THEN** 自动作业保持原进度和身份，暂停中不提交完成效果；恢复消息仍能执行，恢复后再合法完成一次

#### Scenario: 新关准备尚未完成
- **WHEN** 新 Level 已建立，但所需候选或其他业务准备消息尚未提交
- **THEN** 不把建树本身视作全部就绪，开店仍受准备门槛保护，准备完成后才允许正常进入营业

### Requirement: 终态通知与持续作业身份

终态消息 MUST 关联原动作或作业及其所属世界、适用关卡／绑定和阶段。正常运行中，每次实际终态只产生一次业务通知；重放只返回已有事实。关内旧结果不得作用新关；持续厨房作业仍按其存活世界及实例完成，不能机械使用创建时关卡拒绝。终态只表示已提交事实，不建立第二份可写状态或无限历史。

#### Scenario: 上关启动的汤在新关煮好
- **WHEN** 同一厨房与同一锅跨关继续加工，并在新关合法到点
- **THEN** 当前存活作业完成一次并发送有效完成消息，旧关按钮／角色结果仍无权修改新关

#### Scenario: 同一完成通知重复投递
- **WHEN** 相同作业和阶段的完成通知再次到达后继接收者
- **THEN** 不再次加分、增长伙伴、生成后继工作或扣除实物，接收者只认可原提交事实

#### Scenario: UI 已关闭而自动作业完成
- **WHEN** 发起加工的 UI 已关闭，但厨房作业继续存活并完成
- **THEN** 完成事实仍由作业 owner 提交和通知，旧 UI 不写回，新 UI 可从当前投影看到结果

### Requirement: 消息衔接期间的自然收尾

关卡 MUST 将必要前厅业务的待衔接阶段计入真实活动，直到后继工作接入或按规则明确结束。不能利用消息投递间隙提前结算，也不能把尚未执行的工作瞬间做完。角色、餐具、订单及其后继阶段由原 owner 管理，不引入与实际活动分离的替代计数。

#### Scenario: 最后一位顾客离开后的投递间隙
- **WHEN** 营业已收尾且最后一位顾客离场，清桌或必要洗碗仍待消息接入
- **THEN** 保持收尾态；后继实际完成后才产生关卡完成消息，原餐具身份不变

#### Scenario: 第三项伙伴工作完成后领取洗碗
- **WHEN** 伙伴第三项有效完成已经提交，随后通过消息认领洗碗
- **THEN** 领取使用已提交的成长冻结新耗时，重复完成通知不再次增长，正在工作的耗时不重算

### Requirement: 消息结果与投影提交顺序

本地消费者 MUST 在适用版本状态安装后消费相应成功终态，不能因消息先后让界面展示尚未成立的物品或阶段。快照负责当前状态与重开恢复，具名消息负责动作／阶段出口；消费者必须复制独立值并收尾消息。单机保存完成也须经所属消息回到业务提交点，再按原保存合同允许换关。

#### Scenario: 快照和完成结果到达
- **WHEN** 当前客户端收到某版本的作业完成通知
- **THEN** 读取已安装的适用状态，旧世界／旧绑定通知不更新当前表现；消息被回收后已安装值仍有效

#### Scenario: 保存失败后继续营业流程
- **WHEN** 已绑定存档的本关请求保存并继续，而文件操作返回失败
- **THEN** 经消息报告失败并保持原完成关，只有合法持久完成事实重新接入后才允许换关，不由文件回调直接安装新关

### Requirement: 产品边界的真实运行覆盖

每个纳入消息边界的产品功能 MUST 有真实入口、消息投递、业务提交及终点观察的运行证据；自动流程还需证明消息尚未投递时不会提前产生后继效果。验证可以复用同一流程覆盖多项，但不得以其他功能通过或纯方法调用代替未运行的边界。

#### Scenario: 验收一项自动工作
- **WHEN** 测试依次控制开始请求、业务时间和消息投递
- **THEN** 能分别观察接收、开始、到点待转换及最终完成，并验证实际物品或业务阶段只修改一次

### Requirement: 恢复凭证仅在本轮有效
合法加入 SHALL 获得不可猜测的内存恢复凭证，绑定本 Match 和成员。成功 Leave 或整轮停止撤销凭证；错误运行、协议或运行平台、未知或已撤销凭证不得恢复身份，不持久化或公开打印凭证。

#### Scenario: Leave 后使用旧凭证
- **WHEN** 成员已成功 Leave，随后新连接提交原凭证
- **THEN** 恢复被拒绝，不重建原成员或角色

### Requirement: 恢复串行替换连接
合法恢复 MUST 绑定原逻辑成员并建立新绑定代次，不增加逻辑成员。多个有效连接竞争时串行处理，后提交合法绑定替换前者；同一连接重复同一尝试不重复建角色。凭证在本轮保持有效，使回执丢失后可显式新尝试。

#### Scenario: 成功回执丢失后手动重试
- **WHEN** 第一次恢复已提交但 Client 未收到回执，随后发起新恢复尝试
- **THEN** 能以原有效凭证恢复同一成员，最多保留一个当前有效绑定和角色，不重复落物

### Requirement: 当前世界就绪后开放输入
恢复 MUST 以当前关为准建立角色，保持断线落物及空手恢复规则；匹配本人确认、完整投影与视图全部就绪后才开放输入。旧连接答复、动作及快照不能改变新绑定。

#### Scenario: 失联期间已换关且物品被拿走
- **WHEN** Client 在 Host 换关后恢复，而其断线落物已被其他人取得
- **THEN** 原成员在当前关空手出现，不复制或收回旧物品，取得匹配投影前不能操作

### Requirement: 恢复由玩家显式发起
连接失联 SHALL 显示可手动恢复或结束本地尝试，不自动重放未确认业务动作。超时不等于原动作未提交；本地取消未成功送达 Leave 时不得宣称 Host 已删除成员。

#### Scenario: 玩家取消恢复但无法通知 Host
- **WHEN** 网络仍不可用，玩家结束本地恢复
- **THEN** 清理本地等待并显示未恢复，不伪造成功 Leave，其他成员继续运行
