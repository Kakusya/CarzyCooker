# Design

## Context

见 [proposal.md](proposal.md)。已有自动有限批次、液体按份转移、咖啡混杯和原贴单；GridAssemblyConfig当前仅特许热杯液体，其他组合以固体校验为主。本案增加限定的冷杯固液和调饮壶关系，不能简单放宽所有容器。

## Goals / Non-Goals

**Goals:** 三款茶饮各自真实原料、工序、顺序、贴单及保存恢复。

**Non-Goals:** 不做全茶目录、糖度自由组合/封口、无限免费半成品或通用任意容器框架。

## Decisions

定义链按目录P41/P46/P53/P55：取水台热水档从饮用水显式取热水；茶叶+热水泡有限茶底；生珍珠煮制后转入小料罐；茶底+牛奶+糖浆各一份在调饮壶定份混合。叶物料、冰、冷热杯/茶桶/小料罐/调饮壶及必要设备来自源配置初始物资或明确供应；水源如沿原取水点按其显式无限定义，必须形成实际水份投入，不能当设备背景水。

三款成品为热杯茶底一份、冷杯奶茶基底后冰各一份、冷杯熟珍珠→奶茶基底→冰各一份。冷杯与调饮壶只允许其可信配方定义的部分组装、精确数量和前序；未完成混合不能冒充成品。混合最终产物仍沿菜品/内容定义识别，原DrinkAction显式集合、贴单/换绑/一次性杯交付路径保持，未知能力或错序完整拒绝保物。

实际源批次采用Tea=8，资源只包含Basic+Tea；不因使用饮品动作而隐式引入旧Drink资源。SupportsDrinks与资源Includes分开，旧Cafe仍只组合既有资源。Solo1701–1703/合作2701–2703为本批独立菜单链，不抢占后续主题章。

取水台热水档为可信FillWater源，显式接水形成热水76，必须实际在泡茶桶87投入热水与红茶叶77各一份后显式BrewTea；该源沿原无限饮用水定义，不消耗供应配额。首包泡茶产3份红茶底78；原自动批次保留实际输入并逐份扣减。红茶底只能转入热杯59或调饮壶85；调饮壶收一份茶、原瓶装牛奶44、糖浆81后在调饮台MixTea，产2份奶茶基底82，只能分入冷杯84。兼容关系同时由可信源/输出/目标及本关生产许可核对，不放宽其他基底。

生珍珠79沿原单输入替换加工（Boil阶段、BoilPearls能力）实际煮成一份熟珍珠80，放入小料罐86保留原物；从原详情每次取出这一份，再放冷杯。小料罐容量1，不另建无限批次或库存。冷杯84只接收配方有序前缀：奶茶基底→冰，或熟珍珠→奶茶基底→冰；冰83先入、重复份数或逆序均保物拒绝。两种冷饮沿原Assembly显式混合后才成为88/89，并沿原贴单消费一次性杯。

新增动作34–37及能力/阶段沿原请求整数边界，协议41，无新增消息或持久字段，成功格式仍12。半杯清理只特许冷杯84与调饮壶85：完整预检后移除对应固体/液体，保持其余内容；旧混合容器仍拒绝。完成批次的排液仍按原批次整体丢弃剩余成品，不把原料退回。

冷杯“新增材料的合法前缀”与“合法存量”分开：新增仍只允许原有序前缀；明确清理后可以留下原配方的有序子序列（如珍珠＋冰、仅冰），存档允许该实际状态但不补缺料。恢复后不能向错序存量追加以绕过顺序，仍可用对应设施继续清理；其他容器仍沿原校验。普通HUD清理入口按可信FillWater/DrainLiquid/Trash能力显示，新热水档可用原接水动作，冷杯/调饮壶有对应物态就显示原处理按钮。

茶饮关间沿原扩建奖励8，避免新增台面2,13堵住取水台的唯一可达操作格；扩建本身的逐菜单布局校验已在现有入口执行。该配置不改变已验收备料/份数规则，实际文件验收同时覆盖新关间选择。

```text
Host / Solo Fiber / Scene(ProductRoot) + ProcessInnerSender
  +-- Scene(ProductHost) -> HostSession + Ordered MailBox -> HostPeer
  |     +-- Child Match -> Child RestaurantRuntime
  |           +-- Component GridKitchen (items / liquid batches / pearl process)
  |           +-- Child Level (actors / orders / bindings)
  +-- Scene(ProductClient) -> ClientSession + Ordered MailBox -> GridClient
        +-- GridPresentation -> UIComponent / GFEntityComponent
Remote Fiber -> Scene(ProductClient) -> Session + binding -> same client owners
```

取水/批次/盛装/混合经原ClientSession/HostPeer/HostSession统一服务步预检提交，本地sender以ActorId入Ordered MailBox，不向自己UDP；远端沿原公开Proto/wire白名单进入同一入口。自动加工转换沿原内部消息队列，快照先独立安装再发只读Event；handler finally及原Call物理观察者收尾，UI取消不提前回收在途消息。单成员失联仅清本人未执行输入/绑定，持续批次不被退出页面释放。

固液半杯清理限定在本案冷杯/调饮壶：水池排除实际液体并保留固体，垃圾桶处理真实固体并保留液体/受保护外壳，各自完整预检，不退款。已调制成品按其液体定义处理。其他不支持的混合容器仍保持原明确拒绝，不用全局清空隐藏不兼容；补相关主规格/已知边界说明。

新增定义/枚举/供应/工位能力/阶段及菜单消费者先改Luban源，再Check/gen；保留旧菜单值。沿原载荷表达批次/物件/杯内顺序，新增必要字段才升格式并只读适配旧版，旧档不补原料/杯罐。原合作领取与Solo真实文件须覆盖半杯、最后份、未完茶/珍珠以及旧绑定不恢复。

美术沿原export_art.py可编辑模型源生成茶桶、壶罐、茶底、珍珠/奶茶/冰和杯内可辨内容，原Board/HUD只读投影、原owner释放；不手改生成图集布局，不破坏既有动画。

## Risks / Trade-offs

- [固液/顺序校验变松] -> 三配方两模式实际制作、错序错量保物、原咖啡/橙汁受变回归。
- [水被抽象成免费茶/原料份数丢失] -> 显式热水投入、有限最后份争用/清理和文件往返。
- [工作量扩散] -> 仅确认的三款，复用原加工/贴单/资源链，不创建新框架或穷举平衡矩阵。

## Migration Plan

先配置/必要能力及实际循环，再美术/菜谱和两模式入口，最后实际文件及主题章交接。各验收点见execution-notes，不自动提交、归档或构建。
