# Spec Delta

## MODIFIED Requirements

### Requirement: 接收动作和工作完成分离

入口 MUST 快速返回接受或拒绝，最终业务结果在共同 Tick 验证提交后产生。接受、到达、成功启动、加工完成及取消属于不同可观察事实；公共入口不得等待整段行走、加工或营业时间。已经接受的动作 MUST 通过明确的终态消息报告成功、业务拒绝或取消结果；长作业须另外报告其实际开始与结束，不能仅靠快照变化推断完成。单次同步业务的响应可以承担其终点。

#### Scenario: 加工请求已经接受
- **WHEN** 请求得到接收回执但角色尚未到位或加工尚未到点
- **THEN** 显示对应进行中事实，不提前报告物品已转移或加工已完成，其他请求仍可处理

#### Scenario: 烘烤开始与真正烤好
- **WHEN** 开始烘烤命令已执行，而烘烤尚有剩余业务时间
- **THEN** 开始成功与作业开始可分别辨认；仅在真实成品提交后产生该作业完成消息，接收回执不代替完成

#### Scenario: 两条动作先后提交
- **WHEN** 同一玩家较新的动作已经接收，较早动作随后完成或被替换取消
- **THEN** 两条动作分别产生带自己身份的终态消息，不因快照只保留最近命令就丢失较早动作出口，旧结果也不覆盖新动作反馈

### Requirement: 状态事件与启动结果

业务 MUST 先提交所属状态再发布观察事件；事件不替代跨进程消息、请求答复或必须成功的初始化步骤。根启动、监听可用和成员加入各有明确结果，记录处理器异常或发布完成本身不能证明产品就绪。产品功能间的后继执行 MUST 由明确消息请求进入裁决；本地观察事件仅呈现已安装状态，不能直接提交后继功能。

#### Scenario: 初始化失败
- **WHEN** 必需初始化步骤失败，但某个事件发布已经返回
- **THEN** 保留真实失败，不进入已加入或报告 Host 完全就绪

#### Scenario: 成员状态通知
- **WHEN** 发布加入或名单变化事件
- **THEN** 观察者读取已经提交的所属客户端或 Host 状态，不能通过事件形成第二份权威

#### Scenario: 事件观察者处理名单变化
- **WHEN** 已提交名单触发本端观察事件
- **THEN** 观察者只读取当前版本，不再次提交同一变更，不增加名单版本，也不触发另一产品角色的初始化

#### Scenario: 收到一次加工完成消息
- **WHEN** 客户端安装已提交快照并收到对应完成消息
- **THEN** 表现观察者可以刷新成品显示，但不再次生成成品；任何后继业务通过其独立请求接入

## ADDED Requirements

### Requirement: 产品功能的完整消息边界

当前产品的会话、移动实物、加工、顾客订单、前厅工作、清理供应、关卡、布局、Buff、装修和已有单机存档功能 MUST 具有明确消息入口与结果出口；玩家、伙伴、业务时钟和其他功能均遵守此边界。功能内部纯计算及原子效果可以直接调用；框架建树、强制拆树、UI／资源生命周期和旧示例不适用本要求。已有消息入口须复用，不产生平行执行路径。

#### Scenario: 同一功能来自不同触发者
- **WHEN** 玩家或自动调度发起适用于自身身份的同类前厅工作
- **THEN** 均通过明确消息进入同一工作规则，自动来源不能直接完成工作或绕过认领校验

#### Scenario: 确认清理和布局命令结果
- **WHEN** 清理、布局或 Buff 请求被接受后在业务步执行或拒绝
- **THEN** 每条命令产生明确对应结果，消费者无需只观察最近结果字段猜测是否执行

#### Scenario: 查询已有存档
- **WHEN** 用户通过现有选档功能请求浏览或读取一项记录
- **THEN** 请求和成功／失败答复经过本地消息，未合法选定记录不会因此创建运行世界

### Requirement: 自动转换与后继功能经消息裁决

业务时钟到点或上一功能完成时，系统 MUST 发出明确转换／后继请求，再由原领域 owner 在允许的业务步校验并提交。一次阶段转换不得重复执行。跨功能衔接允许经过后续消息轮次；不改变配置时长、暂停规则或单个功能原子效果，不为保持同 Tick 而直接重入执行。必要初始化尚未完成时不得报告业务就绪。

#### Scenario: 加工到点但消息尚未投递
- **WHEN** 烘烤达到所需时间，但其完成转换请求尚未进入裁决
- **THEN** 不提前创建成品，不重复发起同一转换；投递并在允许业务步提交后只创建一份成品并发完成消息

#### Scenario: 清桌完成后安排洗碗
- **WHEN** 清桌完成消息已发出，但洗碗请求尚未提交
- **THEN** 原餐具和待衔接事实仍有明确 owner；投递后只创建一次洗碗工作，直接方法或观察事件不另开第二份

#### Scenario: 暂停时转换等待处理
- **WHEN** 自动加工完成转换仍待处理，此时暂停命令先被提交
- **THEN** 自动作业保持原进度和身份，暂停中不提交完成效果；恢复消息仍能执行，恢复后再合法完成一次

#### Scenario: 新关准备尚未完成
- **WHEN** 新 Level 已建立，但所需候选或其他业务准备消息尚未提交
- **THEN** 不把建树本身视作全部就绪，开店仍受准备门槛保护，准备完成后才允许正常进入营业

### Requirement: 终态通知与持续作业身份

终态消息 MUST 关联原动作或作业及其所属世界、适用关卡／绑定和阶段。正常运行中，每次实际终态只产生一次业务通知；重放只返回已有事实。关内旧结果不得作用新关；持续厨房作业仍按其存活世界及实例完成，不能机械使用创建时关卡拒绝。终态只表示已提交事实，不建立第二份可写状态或无限历史。

#### Scenario: 上关启动的汤在新关煮好
- **WHEN** 同一厨房与同一锅跨关继续加工，并在新关合法到点
- **THEN** 当前存活作业完成一次并发送有效完成消息，旧关按钮／角色结果仍无权修改新关

#### Scenario: 同一完成通知重复投递
- **WHEN** 相同作业和阶段的完成通知再次到达后继接收者
- **THEN** 不再次加分、增长伙伴、生成后继工作或扣除实物，接收者只认可原提交事实

#### Scenario: UI 已关闭而自动作业完成
- **WHEN** 发起加工的 UI 已关闭，但厨房作业继续存活并完成
- **THEN** 完成事实仍由作业 owner 提交和通知，旧 UI 不写回，新 UI 可从当前投影看到结果

### Requirement: 消息衔接期间的自然收尾

关卡 MUST 将必要前厅业务的待衔接阶段计入真实活动，直到后继工作接入或按规则明确结束。不能利用消息投递间隙提前结算，也不能把尚未执行的工作瞬间做完。角色、餐具、订单及其后继阶段由原 owner 管理，不引入与实际活动分离的替代计数。

#### Scenario: 最后一位顾客离开后的投递间隙
- **WHEN** 营业已收尾且最后一位顾客离场，清桌或必要洗碗仍待消息接入
- **THEN** 保持收尾态；后继实际完成后才产生关卡完成消息，原餐具身份不变

#### Scenario: 第三项伙伴工作完成后领取洗碗
- **WHEN** 伙伴第三项有效完成已经提交，随后通过消息认领洗碗
- **THEN** 领取使用已提交的成长冻结新耗时，重复完成通知不再次增长，正在工作的耗时不重算

### Requirement: 消息结果与投影提交顺序

本地消费者 MUST 在适用版本状态安装后消费相应成功终态，不能因消息先后让界面展示尚未成立的物品或阶段。快照负责当前状态与重开恢复，具名消息负责动作／阶段出口；消费者必须复制独立值并收尾消息。单机保存完成也须经所属消息回到业务提交点，再按原保存合同允许换关。

#### Scenario: 快照和完成结果到达
- **WHEN** 当前客户端收到某版本的作业完成通知
- **THEN** 读取已安装的适用状态，旧世界／旧绑定通知不更新当前表现；消息被回收后已安装值仍有效

#### Scenario: 保存失败后继续营业流程
- **WHEN** 已绑定存档的本关请求保存并继续，而文件操作返回失败
- **THEN** 经消息报告失败并保持原完成关，只有合法持久完成事实重新接入后才允许换关，不由文件回调直接安装新关

### Requirement: 产品边界的真实运行覆盖

每个纳入消息边界的产品功能 MUST 有真实入口、消息投递、业务提交及终点观察的运行证据；自动流程还需证明消息尚未投递时不会提前产生后继效果。验证可以复用同一流程覆盖多项，但不得以其他功能通过或纯方法调用代替未运行的边界。

#### Scenario: 验收一项自动工作
- **WHEN** 测试依次控制开始请求、业务时间和消息投递
- **THEN** 能分别观察接收、开始、到点待转换及最终完成，并验证实际物品或业务阶段只修改一次
