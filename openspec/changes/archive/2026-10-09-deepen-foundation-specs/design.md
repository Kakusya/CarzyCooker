# Design

## Context

动机见 [proposal](proposal.md)。已有主规格提供十四个底座模块和两项协作/测试 capability；当前缺口主要在边界场景，而不是模块命名。实际消费者横跨 GF、ET、服务端链接源、导表与协议生成，因此本轮需要统一证据和场景表达。

## Goals / Non-Goals

**Goals:**

- 基于当前源码和配置补足可观察契约，以正常、拒绝、失败、取消、清理和模式条件为场景边界。
- 保留现有要求和场景，增量以 ADDED 为主；只对 ET 固定入口补充实际编译前提。
- 让每个变更可沿有效 Sources 找到对应实现，并显式区分静态证据和运行验证。

**Non-Goals:**

- 不因发现限制修改源码、生成器、Excel、场景、依赖、技能或 AGENTS。
- 不把函数目录清单全部转换成 Requirement，也不复制 Book/SOP 正文作为规格。
- 不裁决未来做饭行为，不建立新业务架构或新的证据/状态工具。

## Decisions

### 1. 在已有 capability 内细化

采用十四个现有目录的 delta，保留 capability 路径，方便后续修改者直接找到原契约。没有发现必须独立成为产品能力的新边界，因此不增加第十七份主规格。与每个类一份规格相比，这样能避免内部重构导致无意义规格迁移。

### 2. 写公开行为与失败语义，不要求维持内部实现

框架 API 的配置 ID、运行 ID、owner、取消结果与输出目录直接影响调用者，保留必要 API 名。内部细节只在 Sources 与本设计中定位。回调逐行算法、生成器每个诊断和全部第三方 API 不进入主规格。

### 3. 现存限制不晋级为正确性保证

ResourceContainer 的回调版本仅在 Create 变更；字典解析非事务且字节切片参数未参与构造；AOT helper 未检查加载返回码。已知问题记录这些事实，相关规格要求诚实表达边界，不承诺自动恢复、全部时序安全或 AOT 已成功。未执行的并发/运行场景不写“已通过”。

### 4. 一次读取范围与精读范围分开报告

扫描排除 Git 对象、Unity Library、PackageCache、Temp、bin/obj、构建、日志和依赖缓存；源码目录 Unity/Assets/Scripts/Library 纳入。只统计二进制路径，不读取素材正文。文本枚举读取用于覆盖核对，语义精读集中在增量 Sources 列出的链路，不声称对数千文件逐行审计。

AOT 接口签名另对已解析包的单个 RuntimeApi 文件作定点只读核对；这是确认调用返回类型的例外，不代表 PackageCache 全量扫描。正式规格引用项目 wrapper，不依赖缓存目录名称。

### 5. 用户本轮授权覆盖完善和同步

用户已明确要求继续扫描并完善 Spec，因此完成增量、主规格同步与文档校对，不停在规划产物。使用现有 OpenSpec apply/sync/verify 工作流组织检查，不请求重复授权；不自动归档、提交或推送。

## Risks / Trade-offs

- 静态场景误被当作实测结果 → 每份变更记录验证类型，产品执行保持 NotRun。
- 同步时漏掉原要求或场景 → 对照同步前 Git 文本，确认原名称和场景都保留；唯一 MODIFIED 保留原场景并补条件。
- 主规格与增量相对引用层级不同 → 同步时转换 Sources 相对路径，并逐一检查文件存在。
- 旧文档状态滞后 → 修正当前进度页中技能数量和已迁入配套；历史迁移记录保持历史语义。
- 细化写入现存 bug → 已知限制单列，正常契约不承诺其不存在；修复另建任务。

## Migration Plan

先核对十四个 delta 与源码，再同步主规格，更新规格索引、模块扫描记录和当前进度，最后完成格式、引用、差异与范围检查。没有部署或数据迁移；用户审阅前保留 change。若需撤销文档改动，只按本 change 的文件差异逐项处理，不还原用户其他改动。
