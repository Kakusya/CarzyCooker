# 做饭产品设计（未实施）

依据 [原始设计资料](../../Book/业务逻辑.txt.txt) A–D、F1–F5、G1–G3。尽量保留适用原文；原文「明确确认」对应已确认，「授权补足」保留历史身份，候选与冲突不晋级。所有内容是未来设计，不是当前能力。目录在 [候选目录](catalog.md)，来源冲突见 [待裁决](backlog.md)。

已对照用户提供的 [设计交接](../handoff/Cooking-设计交接-2026-10-09.md) 和 [禁止项交接](../handoff/Cooking-禁止项交接-2026-10-09.md) 定稿 [八个领域目标规格](specs/README.md)，ET 归属与消息见 [产品架构](architecture.md)。本文提供背景和例子；明确契约及正反场景以目标规格为维护正文。文档定稿不表示业务已经实现。

## A 产品方向与 Host、Client 的关系

### A1 想做的游戏

【明确确认】做菜经营游戏的核心是操作顺畅、物品清楚、能自然分工。玩家共享一家厨房，通过备料、制作、交接和出餐合作，同时逐步改善餐厅。

- 物品真正存在于厨房中，可以搬运、暂存和交给别人。
- 半成品可共享，制作与交付分开，不要求一人从头包办一份订单。
- 餐桌、客流、设备、容器和动线提供经营选择。
- 顾客和固定伙伴让餐厅的变化持续可见。
- 不把日常前厅琐事、员工维护、精细刀工或操作小游戏作为基础负担。
- “食客也是食材”等创新保留为参考，不进入已经收敛的基础玩法。

参考作品主要是《胡闹厨房 2》和《杯杯倒满》。借鉴的是合作、工序和饮品制作方式；下面的菜谱是为本项目整理的游戏配方，不声称是原作的内部规则，也不是现实烹饪教程。

### A2 四种身份必须分开

【明确确认】创建房间的电脑同时运行服务端，并允许本机玩家参与。其他电脑作为 Client 加入。但 Host 的角色不决定存档归属。

| 名称 | 职责 | 生命周期与身份边界 |
|---|---|---|
| Host，房主权威端 | 裁决命令、推进世界、发布状态与成功结果 | 当前会话的运行权威；不自动成为存档 Owner |
| Client，玩家客户端 | 发送操作意图、接收权威结果、显示世界 | 房主本地玩家也走 Client 路径；没有玩法写权限 |
| Participant，协作成员 | 表示协作中的逻辑玩家 | 不等于 Socket，不等于长期 Profile |
| Profile，玩家长期身份 | 持有自己的存档和领取记录 | 稳定业务身份，不等于机器或临时房主 |

一句话示例：**甲可以当房主，加载乙授权提供的存档；甲负责这一场的模拟，乙仍然是原存档 Owner。**

### A3 Match、存档和餐厅运行态

【明确确认】Match 表示玩家建立的协作关系，从成立持续到明确解散。它不是网络连接，不是一个小关，也不是存档。

- 一个 Match 可以有多条 Connection。
- Connection 断开不能自动递归销毁 Match 或逻辑成员。
- 同一 Match 可以跨多个小关，也可以先关闭餐厅，再换另一份存档。
- Match 可以暂时没有餐厅，例如正在选择、传输或校验存档。
- 一份存档选中并校验后，才创建运行期副本 LoadedSave。
- Host 根据 LoadedSave 创建唯一的 RestaurantRuntime，即当前活的餐厅。
- 同一 Match 同时最多有一个未关闭餐厅；不保留多个暂停餐厅。
- 同一餐厅同时最多有一个未结束的小关。
- 小关结束不自动解散 Match。

```flow LR
玩家本地存档 -> 选中并校验: 同平台授权
选中并校验 -> 餐厅运行态: Host 实例化
本地客户端 -> Host: 操作意图
远端客户端 -> Host: 操作意图
Host -> 餐厅运行态: 统一裁决
餐厅运行态 -> 小关成功结果: 成功后产生
小关成功结果 -> 玩家各自存档: 合资格者主动领取
```

### A4 房主本地玩家没有特权入口

【明确确认】Host 本地玩家与远端玩家使用相同的命令验证和快照契约。房主不能通过 UI 或本地函数直接改世界，绕开其他玩家需要经过的验证。

具体传输库和本地接入选型保留待裁决，参见 [待办](backlog.md)。所有玩家走同一裁决路径的产品原则保留。

### A5 运行态结束与跨会话延续

【明确确认】活的餐厅运行态不跨 Match 搬迁。换存档或解散前，先收尾当前小关、处理允许导出的结果、关闭餐厅，再释放资源。

另一个 Match 要继续进度，只能读取存档或正式定义的数据载荷，重新创建餐厅、角色连接和同步基线。不能搬走旧 ET 对象、待执行队列、旧连接或旧快照水位。

首阶段不做主机迁移。Host 关闭、进程崩溃或 Match 解散会终止当前协作运行，不制造业务失败结算，也不能假装成低星成功。已经成功产生的领取凭证另按 B 节处理。



## B 存档归属、授权分支与共同进度领取

### B1 三层权威

【明确确认】必须区分三件事：本地 Profile 授权访问文件；选中的 SaveSlot 提供进度基线；Host 推进运行世界。不能把它们合并成“房主机器拥有存档”。

- SaveSlot 是某个 Profile 持有的一份持久进度记录。
- 未选中的存档只是文件或轻量元数据，不因为扫描目录就展开成运行实体。
- 同一存档每次加载创建新的餐厅运行身份。
- Level 修改餐厅运行态，不直接修改原始存档文件。
- 稳定的 ProfileId、SaveSlotId、revision 与运行实例身份分开。
- 文件路径、磁盘盘符、文件句柄和引擎对象不进入网络载荷或存档业务身份。

### B2 平台边界

【明确确认】目标包括 PC 与 Android，但两者是隔离的产品生态。

PC 与 Android 不互联，不共享 Match、Profile、SaveSlot、授权包、成功结果或领取凭证，也不支持相互导入。共享纯 C# 游戏逻辑不代表共享玩家数据。

存档默认落在各平台的应用私有持久目录。平台适配器负责找到目录；领域规则只处理逻辑 ID。用户显式导出文件与内部存档记录是两个入口。

### B3 授权副本：导入立即成为独立分支

【明确确认】采用持有授权包即可使用的 bearer 方式，同平台的合法接收者可以导入。

1. 原 Owner 导出带来源身份、修订和授权信息的副本。
2. 接收者选定自己的本地 Profile，校验授权后导入。
3. 导入成功立即创建新的 SaveSlot，归接收 Profile 所有。
4. 新分支记录来源，但不能写回原始 SaveSlot。
5. 新 Owner 可以在原 Owner 不在线时独立开局、继续推进自己的分支。

源档和各分支永久视为不同存档，可以同时存在。禁止根据时间戳或谱系自动合并，也不能把最新分支自动覆盖回源档。

谱系至少记录：新 Owner、直接来源 Profile/SaveSlot/Revision、根 Profile/SaveSlot、授权身份。谱系用于追踪和展示，不等于写入权限。

**区别：**提供原存档的授权包，与成功小关后发给参与者的领取凭证，是两种不同凭证。

### B4 成功小关产生共同结果，不自动写所有人的文件

【明确确认】Level 启动时冻结有资格领取的参与者名单。只有该开局名单内的参与者可以领取本关结果；后来加入 Match、没有参加本关的人不能领取本关进度。

- 小关成功原子提交后，Host 产生不可变 SaveResult。
- 每个合资格 Profile 获得独立、稳定的领取凭证。
- 各玩家主动领取，系统不自动把结果写进所有设备的 SaveSlot。
- 某人未领取或暂时断线，不影响别人，不回滚小关成功。
- 成功提交前崩溃、中断或技术失败，不产生可领取结果。

### B5 凭证发送、持久化和 ACK

【明确确认】Host 发出凭证；Client 持久化凭证后才 ACK。ACK 证明客户端已保存凭证，不能当作已领取成功。

未 ACK 不阻塞其他人，Host 在 Match 存续期间重发同一凭证，直到收到 ACK 或 Match 终止。不能每次重发都创建新的结果或资格。

| 事实 | 含义 |
|---|---|
| 小关成功提交 | 世界和本关成功结果已确定 |
| 凭证发出 | Host 尝试送达领取资格 |
| 凭证持久化 ACK | Client 已保存资格，可按规则离线处理 |
| 领取提交成功 | 本地存档新建或覆盖已完成，资格被消耗 |

### B6 领取时新建或显式覆盖

【明确确认】玩家选择新建 SaveSlot，或显式覆盖本次授权谱系范围内允许的现有 SaveSlot。

- 新建：分配新存档身份，归领取者 Profile。
- 覆盖：有损替换，不合并旧内容。
- 覆盖目标可以不属于领取者 Profile，但必须通过目标身份、授权范围和预期修订检查。
- 知道某个谱系 ID 不等于获得覆盖权限。
- 覆盖不改变目标存档原有 Owner。
- 事务提交期间保护旧记录；成功后不保留上一版本或用户可恢复备份。
- 身份、授权、修订、容量或磁盘写入失败，不消耗凭证，可以重试。
- 只有原子写入成功后，才记录领取成功并消耗资格。

同一设备的本地 repository，对同一 SaveResultId 与合资格 ProfileId 最多成功领取一次。重复请求返回原领取结果，不再次创建或覆盖。

**明确接受的限制：**没有中心服务时，同一凭证复制到同平台另一台设备，可以再次形成独立本地分支。不承诺跨设备的 Profile 全局一次性。

### B7 正常解散与异常终止按 Client 各自观察判断

【明确确认】Client 收到并持久化 normal-close receipt 后，关闭本地尚未领取的资格。

未收到正常关闭回执的 Client，按它观察到的异常终止处理，可以保留已经持久化的未领取凭证。离线条件下，不同 Client 可以对同一 Match 有不同终止观察。

正常关闭回执只能关闭实际收到它的本地凭证副本；不能撤销另一台未观察到回执的设备上的复制件。

### B8 保存规则与尚未做完的协议

产品检查点只在小关成功结束、结算收口后写入。准备中、营业中、半条命令、失败现场都不覆盖最近成功检查点。技术同步快照、诊断恢复载荷和玩家产品存档是三个不同用途。

写入要检查预期 revision，先暂存，再完整提交；失败不把有效旧记录破坏成半份新记录。损坏或未知版本不能静默当成新档。

【未决】授权包如何签发、验证、撤销和保护密钥；正常关闭回执的认证；跨设备传输 UX；是否需要同平台中心服务；完整断电故障模型。上述产品语义已经确定，不代表安全和持久化协议已实现。



## C 大关、小关、顾客与固定伙伴

### C1 一个大关持续经营同一家餐厅

【明确确认】一个大关包含多个递进小关。后续小关承接同一家餐厅的物料、设备与积累，不是互相独立的餐厅副本。

Kitchen 属于餐厅运行态，与 Level 并列。小关结束可以释放本关对象，但不能顺带毁掉需要延续的厨房。

```tree
一个大关中的同一家餐厅
  厨房持续存在
    物品、容器、工位、加工、供应
  当前小关
    顾客、订单、营业时钟、评分
  小关成功后
    收口、写成功检查点、下一关准备
```

不新增与小关并列的独立“关间准备”业务对象。准备、装修和选择服务于下一小关；可以利用小关自身的 Preparing 状态。

### C2 自然营业完成，不设置正常业务失败

【明确确认】小关包含营业时间与收尾时间。

- 营业时按配置间隔来客，节奏可预测。
- 收尾停止新来客，处理已到店顾客和必要前厅收口。
- 顾客满足后用餐离席；未完成订单的顾客超时也离席。
- 未满足订单计 0 分，不倒扣，不导致整关失败。
- 服务收口完成后自然成功；没有“必须够多少分才能过关”。
- 原工程的 Failed/Retry 只是兼容或技术能力，不能重新推出失败界面。
- 网络中断、Host 关闭、运行异常与自然成功分开。

【授权补足】有队列、行走顾客、待清桌与人工工作后，自然结束要等待这些必须完成的前厅活动排空；不要求销毁所有半成品、清空后厨或搬完所有在途货物。

### C3 第一版评分

【明确确认】每个订单配置固定基础分；成功交付只计一次。总分是成功订单基础分之和，按关卡阈值显示 0–3 星。

0 星仍自然完成，不阻止下一小关。第一版星级不影响装修、Buff、解锁或存档奖励，不加入连击、速度倍率、菜品质量或复杂经济。

早期“收益、评价、完成订单数”的结算想法要与这个后来的最小评分合同区分。货币收益和顾客评价仍是设计方向，未确定完整规则。

汤 100 分、吐司 50 分、阈值 100/200/300，以及两菜轮换，是历史临时基线，不是正式平衡。

### C4 成功后保留什么、重置什么

【明确确认，含后续授权细化】

| 保留到下一小关 | 本关结束后重置 |
|---|---|
| 食材、半成品、成品和剩余份数 | 本关订单、目标与得分上下文 |
| 容器及内部内容、脏净餐具 | 顾客、座位服务状态与营业时钟 |
| 未完成加工及已做进度 | 人工工作认领与本关临时工作状态 |
| 已确认装修、解锁及实际布局 | 本关命令与快照的旧代际权限 |
| 与实物一致的供应余额、在途和待收货 | 伙伴本小关成长计数与解锁能力 |

成功后不是再把标准初始物品叠加一遍，不能复制食材或把剩余批次回满。玩家进入下一小关使用下一关的初始出生位；同小关技术恢复则保留合法位姿。

工位升级时，未完成加工迁移到新工位，保留进度。加工属于厨房，通过稳定业务引用关联工位，不因更换工位而换一份加工身份。

旧纪要先说 NPC 进行中任务延续，后来明确改成结束时收口、不把进行中状态带过去。最初自动路径按完成效果收口；新增人工前厅路径要通过自然结束检查，不能强制完成玩家没做完的服务。见 [待裁决](backlog.md) 的适用范围。

### C5 装修、解锁与 Buff

【明确确认】成功后展示剧本或关卡定义的候选装修方向，玩家选一个。装修同时影响厨房工位种类/数量、空间布局、餐桌和 NPC 设施。

- 新道具 ID 表示 DefinitionId，即解锁一种道具种类；不是跨关复用某个运行实例 ID。
- 下一关按其配置供应解锁设备，数量由配置决定。
- 候选全部展示；冲突组合由候选池避免。
- 不设计重复获得同一 Buff 的叠层问题，不同 Buff 不设通用互斥。
- 已确定选择随成功结果进入检查点，准备变化不独立写盘。
- 首个新设备例子是烤箱；首个 Buff 例子是煮制加速。

**Buff 的最后明确修正：**Buff 的配置和生效状态属于当前加载的 Level。重连只接受 Host 同步的当前 Level Buff，不由玩家私有状态覆盖。下一关依新 Level 加载内容生效，不能把早期“整个大关”说法解释成 Match 全局自动继承。

【授权补足】已解锁权限与本关允许集取交集。解锁过某道菜或设备，不代表每关都允许使用。

保存检查点失败，停留在成功收口后的状态，阻止安装/公布下一关；可以重试保存，不能假装已保存。

### C6 顾客与餐桌的设计理念

【明确确认】采用“可见顾客＋自动服务＋餐桌控制客流”的半抽象方向。

- 顾客真实进入并使用餐桌，持续反馈餐厅状态。
- 餐桌影响接待容量、订单波峰与动线，不只提供装饰。
- 不默认要求玩家逐桌带位、送水、收银、清洁。
- 顾客入座后，伙伴询问完成才生成订单；订单不凭空由厨房生成。
- 顾客等询问不产生额外惩罚，只占用桌位、影响节奏。
- 顾客收到食物后仍短暂占桌用餐，不马上腾出桌子。
- 订单和顾客使用独立稳定身份，不能拿桌号当顾客或订单身份。

【授权补足】顾客过程可表达为到店→排队→走到桌边→等待询问→已点单→用餐→离开。排队有界且 FIFO；不能无限生成客人。

大小桌差异、团体客、儿童客、偏好、氛围加成和具体收益模型只是候选方向，没有全部确认成正式规则。

### C7 NPC 是固定伙伴

【明确确认】伙伴数量少，开局就有固定几位，具有名字和稳定身份，长期陪伴同一家餐厅。不是可反复招聘、替换、拼数值的普通员工。

- 身份、名字、固定岗位和陪伴长期保留，跨大关不变。
- 能力成长只在当前小关有效，每个小关重新成长。
- 一位伙伴对一个固定岗位负责，玩家不安排岗位或局内指派。
- 伙伴自主认领岗位任务，按生成顺序处理，不增加复杂优先级微操。
- 当前暂定 1 位，最终人数没有确定。
- 询问和洗碗占用时间，伙伴同一时刻不能同时做两件事。
- 原最小路径有询问优先、无询问再洗碗的既有规则；更通用跨岗位调度没有确定。
- 关间没有营业任务，伙伴站在一边可聊天；聊天仅提供氛围，不改变数值。

希望伙伴提供可见的正面反馈，减少低价值琐事。人格事件、庆祝动作、三层工作总结属于建议，没有确定具体内容；工资、疲劳、饥饿、心情等维护槽也没有纳入基础规则。

### C8 第一项伙伴成长已定到公式

【明确确认】完成 3 个伙伴任务后，解锁洗碗加速。

- 伙伴询问完成与洗碗完成都累计 1 次；未完成不累计。
- 洗碗耗时 = `max(1, ceil(基础洗碗 Tick / 2))`。
- 接任务时冻结需要的 Tick，已开始任务不半途改速。
- 第三项任务完成后，同 Tick 后续新认领的洗碗可立即享受加速。
- 下一小关与失败重开清零；同小关技术恢复保留。
- 完成任务数是唯一可写成长来源；解锁从数量和阈值推导。

早先希望成长解锁处理方式或覆盖范围，后来明确允许首项采用速度加快。不能把早期原则当成禁止已确认加速的依据。

【授权补足】玩家可选择接手前厅工作，但不是给 NPC 下命令。一个任务只有一个执行者；玩家停手或离开保留进度、释放认领，伙伴可以接续。玩家完成的任务不计伙伴经验，伙伴实际完成才累计一次。



## D 物品、操作、加工与订单

### D1 一格一物与容器内部不是一回事

【明确确认及授权补足】普通手持槽一次拿一个物件，普通台面一次放一个物件。这个物件可以是一份原料，也可以是内部装多个成分的锅。

- 容器本身也是物品，拥有一个稳定身份和唯一位置。
- 搬走锅、盘、碗时，内容随容器一起移动。
- 原料、半成品和成品是可识别、可暂存的物件。
- 同一物品不能同时在手里、桌上和锅里。
- 容器容量与可接受类型由定义声明；不能用容器内容绕过普通空间占位。
- 同类原料不默认合并成一个无限堆叠物件。
- 特殊货架、设备槽、餐具池、包装有各自声明的容量。
- 包含关系不能成环。

### D2 移动与交互

【授权补足】角色自由连续移动，物件放置可以用离散槽位，两者分开。

- 操作受位置、朝向、距离与障碍约束。
- 停止移动保留朝向，斜走不额外加速。
- 玩家间有空间关系，不能随意重叠或远程拿物。
- 按同一规则做交互预览，执行时再次验证。
- 多个目标以朝向、距离和稳定 ID 决定，不根据不稳定遍历顺序跳来跳去。
- 空手面对物件拿取；持物面对兼容容器添加，面对空槽放下。
- 满台面或不兼容时给拒绝原因，保留手上物品，不偷偷换一个目标。
- 目标高亮、手持物显示和整体俯视/斜俯视是表现目标，不能由纯逻辑运行证明手感达标。

投掷、接取、冲刺后置；不把普通落地堆积或任意堆叠作为通用规则。

### D3 七项基础动作与后续扩展

【明确确认】最初厨房动作：拾取、放下、放入、取出、启动加工、倒出、提交。每项是完整验证后原子提交的命令。

后续【授权补足】增加连续移动、手工作业继续/停止、按份盛装、清空、普通物件丢弃、订单绑定/解绑/换绑、采购/接收和人工前厅接手。这些是明确能力扩展，不能假装最初七项已经覆盖全部行为。

### D4 手工与设备作业

【授权补足】手工加工需要持续参与，设备加工启动后自动继续。

- 一项手工作业只有一个执行者，松手或离开暂停并保留进度。
- 别人接手不重置，不因同时两人操作默认加速。
- 一个工位同一时刻只进行一个加工，两个切配并行需要两个工位。
- 设备自动加工不要求玩家一直守着，不引入自动运输、投料或出餐。
- 番茄蛋花汤的锅启动后不能取消；端走锅仍继续加工，输入锁定。
- 完成后成果可以留在原处，等玩家或队友取走。
- 全局 Pause 停止统一业务时钟；动画不能决定加工完成。

### D5 两类完成形态

【明确确认】切配等预处理消耗旧输入，生成新的半成品物品实例。例如完整番茄→番茄块，不在旧番茄上随意叠可写状态。

锅类多输入加工可以保留输入，容器变为已完成状态；真正倒出时才生成独立成品。例如煮好的蛋花汤先留在完成锅中，盛到碗里才成为碗中成品。

配方由投入自动识别，玩家显式启动，不额外打开配方选择菜单。单步输入按种类与数量匹配，先后顺序不重要；完整菜谱的阶段依赖仍然必须遵守。

### D6 批量、分装与守恒

【授权补足】一锅或一壶可多份，显式记录产量与剩余份数。

- 按份盛装一次取一份，源余额减少一，目标增加一份。
- 取最后一份时结束该批次、消费原输入并复位源容器。
- 两人抢最后一份，只能一人成功。
- 目标满、类型不符或不可达，源不减份、目标不增物。
- 多份完成容器必须用按份动作，不能复用旧 Pour 凭空倒出整批。
- 未完成内容的整体 Pour 保留其明确转移语义；完成单份维持既有行为。
- 完成批次不能追加原料、取出原加工输入或重复启动。
- 暂存、搬运、换人或跨关都不能把已消耗份数回满。

### D7 错误操作与垃圾处理

【明确确认及授权补足】可预判的错误材料在放入时拒绝。合法投入但已不需要的内容允许显式清空。

- 清空删除内容和批次，保留容器身份、位置和脏净状态。
- 丢弃只销毁允许丢弃的普通物件，不默认删锅或设备。
- 不给清空产物、不加分、不退库存，不隐式回收原材料。
- 正在加工且锁定的输入不能被拿走或清空。
- 嵌套容器不能被清空顺带销毁，先取出再处理。
- 拒绝不能先扣料、搬物或分配半份结果后再报错。

基础版本不加入过熟、烧焦、火灾、故障、保质期、地面污渍或经济处罚。

### D8 配方身份与订单身份分开

【明确确认及授权补足】先做菜，再分配给订单是合法的。配方完成不等于已交付，放普通台面也不等于提交。

- 饮品完成后独立绑定订单，再交付。
- 餐食、甜品不强制加贴标签手续，提交时核对订单。
- 绑定不改变配方内容。
- 交付前允许显式解绑或换绑；先验证新目标，不能失败后丢掉原绑定。
- 同一成品不能重复绑定给冲突订单；同一订单不能重复结算。
- 按配置交到统一出餐口或对应顾客餐桌，不能信任 Client 随意传的桌号。
- 新饮品出餐杯按当前目录采用一次性消耗；盘、碗走可洗餐具回收。补杯是供应的一部分。
- 封口或盖子并入交付表现，不新增每杯单独封盖工序。

### D9 最早完整代表菜：番茄蛋花汤

【明确确认】代表菜必须同时覆盖多输入、半成品、持续加工和装盘。

1. 顾客入座，伙伴到桌边询问若干 Tick，生成“碗中蛋花汤”订单。
2. 取得番茄与鸡蛋；番茄直接可切，不加洗菜步骤。
3. 在砧板切番茄，消耗原番茄，生成番茄块。
4. 鸡蛋放入碗，手持碗即可启动打蛋，不需要工位；生成蛋液。
5. 将蛋液倒入锅，碗空出来，可以继续用来装汤。
6. 将番茄块加入锅。此代表菜的水为默认供应，不占物品和容量。
7. 在灶台显式启动煮制，跨多个 Tick；端走锅也继续，不可取消。
8. 到点后锅成为完成态，输入仍留锅中。
9. 倒入碗，生成独立汤物品；提交碗和汤。
10. 顾客占桌用餐后离席；碗变脏，伙伴空闲时洗若干 Tick，回干净碗池。

干净碗数量有限，压力来自并行订单数量；一个碗可先打蛋再装汤，不强制每一步都占一个新碗。

第一道烤箱例子是烤面包：面包片→显式启动烤箱→消耗面包片、生成烤面包。最初它只作为半成品，后来另一个增量才成为盘装可点单菜品。不能把这个变化当成同一时刻的矛盾。




## F 工位、供应与布局

### F1 工具服务于统一玩法语法

【明确确认及授权补足】道具定义与运行物件分开。固定工位提供能力，可搬运容器保存输入、加工或盛装内容。锅既是可搬物品，又可具有容器能力，不另造同一锅的第二个身份。

相同动作规则支持不同食物：统一取放、添加、启动、取成品、分装。不要每加一道菜就写一套专用交互。设备模式可以区分，例如蒸汽机的加热与打泡，不让一种模式偷偷提供另一种结果。

### F3 容器设计

- 加工容器：锅、平底锅、搅拌盆、果汁壶、茶桶、奶缸、配料罐等。
- 特定载体：模具、烤盘、蒸篮、炸篮，按步骤校验实际容器身份，不能只记一个工具名字。
- 出餐容器：餐盘、汤碗、披萨盘、蒸食盘、大餐盘、出餐小锅、甜品盘/杯、热饮杯、透明冷饮杯。
- 整锅制成小火锅时，换到出餐小锅，不把后厨煮锅交给顾客。
- 杯、碗、盘的容量与兼容性独立配置，不因中文都叫“杯”就互换。
- 烤箱加工用的模具或托盘不能直接充当任何订单的出餐容器。

### F4 有限与无限供应分开

【授权补足】供应者、采购请求、等待到货、接收、实物包装、仓储和单份材料是不同阶段。

- 无限取料点每次给一份，放入空手；只有显式配置为无限的来源才这样工作。
- 有限库存先申请并预留，再等待固定 Tick 到货。
- 到货后要在收货位置接收，生成实物包装与内部材料。
- 收货槽满时保留待接收货物，不吞货、不先扣完再失败。
- 搬包装、拆份、暂存与加工使用同一物品系统。
- 不同时维护两套能独立消费的“库存数字”和“实物数量”。
- 采购包装量与配方投入份数分开。
- 准备与营业可补货；收尾禁止新申请，已批准货物照常到货。
- 在途和待接收货物允许随成功跨小关保留。
- 暂停不推进到货时钟；重复申请或接收不复制货物。
- 清空或丢弃是损耗，不自动退款或回库。

首轮不加入采购价格、违约罚款、取消采购或完整经济系统。实际包装量、外部余额和到货时间是配置/待平衡值。

### F5 布局与装修

【授权补足】准备态可移动、旋转设备或扩可用区域；营业中不搬设备。布局服务于玩家、顾客和物料动线。

- 可以表达地板区域、墙、设备占地与旋转、交互面、出入口、队列、餐桌、出餐口、收货、仓储和清洗位置。
- 占地和设备能力来自可信定义，玩家请求不能把设备缩小以绕过碰撞。
- 占位、通路、角色半径净空、权限与现有物品/加工引用整体预检。
- 改动一次原子安装；非法布局保留旧现场，不半搬完才发现出口被堵。
- 顾客和玩家读取同一有效地形，不能用两张互相矛盾的地图。
- 移动已有工位保留其物件、容器和合法加工进度。
- 缺少承接位置时明确拒绝，不删除食材或凭空落到任意位置。
- 扩建先表达可用区域，不把购买价格、关号或永久权限写死。
- 在准备中可以用同一厨房备料和申请物资；不开始客流、开单和提交。

“生产线更好走”是最终可玩目标，逻辑通路验证不能代替镜头、按键与实际合作手感。


## G 权威、命令与重连原则

### G1 固定 Tick、单一 writer 与统一时钟

【明确确认】网络回调只收发、解帧和入队。Host 的固定 Tick 统一校验、裁决和提交；烹饪、顾客、伙伴与供应都用这一个业务时钟。

- 逻辑 Tick 不等于渲染帧、墙钟或动画回调。
- 首阶段权威状态同步，不做严格 lockstep。
- 首阶段全量状态快照，不急于 Delta/Diff 压缩。
- Client 被动显示，不先做预测、回滚或客户端权威。
- 30Hz 只是原型候选，未确定正式频率。
- 网络先到先得用入队时原子分配的接收序号；不能由线程再次争抢决定。
- 原单机按 Tick、玩家 ID、命令序号稳定仲裁，不静默混用两种排序。

【授权补足，待本项目对齐】每个可变状态族有唯一 writer 和释放责任，适配器不再维护一份可写真相。现有底座保持；这些产品领域规则尚未实施。

### G2 命令与消息的可靠性边界

【明确确认及授权补足】命令必须检查身份、资格、代际、距离、容量、占用、版本和重复。

- 同业务 ID、同载荷重试，不再扣料、不再生成、不重复结算。
- 同 ID 不同载荷明确冲突，不能当作新指令执行。
- 旧 Level、旧连接代次和旧会话命令失效。
- 消息携带协议版本、种类、Match/Level、发送者、顺序和关联信息。
- 版本、必填字段、枚举和大小限制明确校验，不静默兼容未知规则。
- Command、准入、最终处理结果、已提交事件、完整快照、传输 ACK 和业务 Ready 是不同事实。
- 网络发送成功不代表对方应用了完整状态，更不代表业务成功。

【历史工程细化，待本项目对齐】已经提交的命令效果、事件和 Executed 终态，在随后 fixed-step 失败时保留；本帧 Tick 不推进。不能把重构变成整帧回滚。监听异常不等于业务回滚。

### G3 断线、重连与暂停

【明确确认】Client 断线，Host 可以继续当前小关；Host 单方面控制暂停和恢复，Client 重连不自动恢复营业。

- 断线后取消该连接尚未执行的命令，释放该玩家工作占用。
- 已经原子提交的动作和订单结果保留。
- 原 Client 可找回原 Match 成员；成员身份与 Connection 分开。
- 重连凭证在同一 Match 内跨小关有效；Host 关闭、Match 解散后失效。
- 每个成员同时一条有效 Connection，新绑定撤销旧连接的命令权。
- 重连接收当前完整状态，不重放断线期间的历史命令。
- 玩家角色恢复初始化位置/临时状态；厨房、订单、供应、装修和 Buff 以 Host 当前世界为准，不回滚。
- 暂停期间允许连接控制与完整状态同步，业务时钟保持停止。
