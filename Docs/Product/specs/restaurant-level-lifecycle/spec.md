# restaurant-level-lifecycle Target Specification

> 状态：目标规格文档已定稿，业务尚未实现；已确认、授权补足与未决范围见 [规格索引](../README.md)。

## Purpose

定义同一家餐厅跨递进小关持续经营的目标行为，明确自然成功、评分、准备态、装修和检查点之间的顺序。本文是未来设计规格，既有 ET 示例并未实现餐厅生命周期，也不因此授权一次性交付全部玩法。

## Requirements

### Requirement: 厨房与当前小关分离

RestaurantRuntime MUST 持有持续 Kitchen 和最多一个未结束 Level，两者释放归属并列；小关结束不销毁厨房。下一关准备使用新 Level 的 Preparing，不新增独立关间准备业务 owner。

#### Scenario: 成功释放本关对象
- **WHEN** 当前小关完成收口并结束
- **THEN** 顾客与订单等本关对象可释放，厨房物品、加工、布局和供应仍属于原餐厅

### Requirement: 自然营业与必要前厅排空

Level MUST 在营业时按配置来客，收尾停止新来客并自然排空既有排队、行走、座位服务、用餐、待清桌及必要人工工作；不要求清空后厨、搬完货物或完成所有厨房加工。技术中断不得假冒正常完成。

#### Scenario: 后厨尚有剩余汤及在途补货
- **WHEN** 必要前厅活动已经排空，后厨仍有半成品与在途货物
- **THEN** 可以自然结束营业，保留这些厨房和供应状态，不强行销毁或补齐

### Requirement: 固定订单得分与零星成功

第一版 MUST 对成功交付订单按配置基础分只计一次，未完成订单计零且不倒扣；总分按关卡阈值显示零至三星。零星自然完成并允许继续，星级不决定装修、Buff、解锁或存档奖励，不引入连击、速度或质量倍率。

#### Scenario: 没有完成任何订单
- **WHEN** 全部顾客离席且前厅合法收口，总分为零
- **THEN** 正常成功并显示适用星级，不出现业务失败或强制重试

### Requirement: 跨关保留与重置

成功换关 MUST 保留食材、半成品、成品、剩余份数、容器脏净、加工进度、布局解锁、实际供应余额、在途与待收货；重置订单顾客、座位服务、时钟得分、工作认领、伙伴关内成长及旧关权限。不得叠加标准初始物资、补满批次或复制补货。

#### Scenario: 半锅汤进入下一关
- **WHEN** 当前批次只剩一份并随成功结果进入下一小关
- **THEN** 仍只剩一份，容器身份和厨房位置按承接规则保留，不恢复整锅产量

#### Scenario: 角色进入下一关与同关恢复
- **WHEN** 玩家进入下一小关或执行同小关技术恢复
- **THEN** 前者使用新关出生位；后者按适用技术恢复保留合法位姿，两者不能混用

### Requirement: 装修选择与加工关联稳定

成功后系统 MUST 展示配置候选并选一个装修方向，候选池避免冲突；解锁表示定义种类，数量按下一关配置。工位替换只变更加工的合法关联，不销毁原加工身份或进度；布局选择随成功结果进入检查点，不单独保存准备现场。

#### Scenario: 升级正在加工的工位
- **WHEN** 合法装修用新工位承接未完成加工
- **THEN** 保持加工身份与进度，原子更新工位关联，不重做投料或重新开始计时

### Requirement: Buff 和关卡许可有明确范围

Buff MUST 归当前 Level，重连使用 Host 当前生效状态，下一关依新配置加载，不作 Match 全局继承。已解锁权限与本关允许集取交集，不设重复同 Buff 叠层或通用异 Buff 互斥。

#### Scenario: 已解锁配方在新关不允许
- **WHEN** 玩家持有配方解锁，但新 Level 允许集未包含它
- **THEN** 不获得本关新生产资格，不能通过客户端历史 Buff 或解锁缓存绕过规则

### Requirement: 许可缩小保留旧物和已受理工作

换关许可缩小时系统 MUST 保留旧物、剩余批次和已受理工作，允许合法货物接收、搬运、清理及已开始手工工作的接续；禁止被限制内容的新采购、投料、启动和新盛装。此项为交接中的授权补足，正式交互提示仍需设计。

#### Scenario: 旧批次已不在新关许可内
- **WHEN** 厨房保留该批次，玩家请求新盛装
- **THEN** 拒绝新盛装且不删除批次，仍可按规则搬运或清理

### Requirement: 成功检查点阻止过早安装下一关

系统 MUST 在成功收口后完成适用检查点提交再安装或公布下一关；保存失败保持收口状态并允许重试。不得发布下一关后再宣称失败写入已经成功，也不把技术失败解释成低星结算。

#### Scenario: 检查点写入失败
- **WHEN** 小关已成功收口但检查点提交失败
- **THEN** 不安装下一关，不破坏旧有效记录，可重试当前提交
