## A Owner 明确禁令与工程行动边界

### A1 禁止 SHA 校验

来源：根 `AGENTS.md`，2026-10-09 Owner SHA 校验禁令。

- 模型不得执行、要求或委托任何 SHA 校验。
- 包括 SHA-1、SHA-256、文件／产物／源码 hash 比对、批量 hash 清单和精确 SHA 审阅。
- 不得把它作为研究、审计、测试、提交、推送、恢复或交付前置。
- 不得借脚本、工具、执行者、旧门禁、dot 工作流或技能间接实施。
- 历史文档保留的要求不恢复效力；只有 Owner 明确改变规则才有例外。

### A2 禁止额外 JSON 证据与全量状态副本

来源：根 `AGENTS.md`，2026-10-09 Owner JSON 证据产物禁令。

- 不新增展开、美化的 JSON 证据或全量状态快照及副本。
- 不新增证据包、快照归档或批量 hash 清单。
- 测试原始输出只留原输出目录，不复制到 research、evidence 或其他归档目录。
- 不把测试原始输出提交 Git 或推送。
- 排查只读必要字段，不在终端或报告输出完整 JSON 状态。
- 报告只保留简短结果、失败原因、原日志路径和退出码。
- 压缩、单行化、改名不能绕过；“为了可追溯”不能增加授权。
- 只有 Owner 后续指定具体产物，才允许对应例外。

这条约束的对象是模型额外制造的证据与状态副本；既有业务协议和存档的数据格式仍由其正式契约定义。整理交接不授权修改这些协议。

### A3 禁止自主扩写测试框架控制

来源：根 `AGENTS.md`，2026-10-09 Owner 测试范围约束。

- 不继续把被否定的 88 项框架控制作为工作目标。
- 不自主新增或扩写“测试测试框架”的控制套件、断言清单或合成状态／证据。
- 不自主增加 mock/fake、反射私有实现测试或故障注入套件。
- 不以覆盖率、控制数量、审计完整性或“修复前置”扩大范围。
- 不运行旧 rich／NetworkRichRecoveryAcceptance 入口。
- 仅使用 Owner 指定的新 Cooking FlowAcceptance 与真实 Flow 场景。
- 新场景必须有 Owner 指定的可观察行为、输入和预期结果。
- 框架专用测试必须由 Owner 指定该具体场景；不能把框架内部校验变成产品目标。
- 执行者不得追加测试文件、控制 profile/request/rule 或测试专用入口。
- 超范围测试改动不接受，不再派生“补齐测试”的任务。
- 不用控制 Passed 数量替代产品验收或完成进度。

旧代码和记录如何舍弃、删除或保留由 Owner 决定。禁止扩写不等于授权助手自行删掉原有东西。

### A4 禁止恢复旧工程、扩大产品范围

来源：本轮放弃项目的指令，以及根 `AGENTS.md` 的暂停和 Cooking 范围规则。

- 不沿用已删除 Issue、旧派发、旧规划或旧合并授权恢复工程。
- `orca-ready`、P0 标签、报告、草案和历史 completed 不增加授权。
- 不修改 Shooter、MOBA、Orleans 等其他示例的代码、配置、协议、脚本、测试或门禁。
- 不把示例修复、迁移、全仓回归当作 Cooking 隐藏前置。
- 共享工具或框架改动必须对应已批准的 Cooking 具体需求，逐文件说明消费者、必要性和验收。
- 不清楚 Cooking 关联时，停止该部分实施，不能凭“统一基础设施”扩大范围。
- 已有越界改动不得因测试通过就合入 master；保留其来源，不能借旧整项授权接纳。
- 当前文档整理不授权构建、测试、启动服务、修改环境、提交、推送、合并或发布。

### A5 禁止破坏用户现场与派生工作树

来源：根 `AGENTS.md` 的 Orca 与工作树约束。

- 不用清空、reset 或全局 kill 处理任务。
- 不清理用户工作树、备份、进程或未提交修改。
- 保留用户解决方案及 Practice 目录。
- 工作树只能由根协调者直接创建。
- 非主工作树中的 worker、agent 或终端不得创建后代工作树，也不得委托别的会话代建。
- 需要新隔离时，上报根协调者；根协调者仍须有本轮范围授权。
- worker 停止不等于分支可删；状态文件不能证明进程还活着或已经结束。
- 跨树来源搜索不授权修改或清理被搜索的树。
- Windows 递归删除或移动前，必须核对绝对目标属于授权目录，不能跨 shell 拼接删除命令。
- 不提交本机 developer、runtime、cache 或 log。

### A6 禁止用文档、测试和标签冒充事实

来源：根 `AGENTS.md` 的结果与证据规则。

| 不得作出的推断 | 应记录的事实 |
|---|---|
| 没运行、缺环境、零覆盖、旧产物算通过 | NotRun、Blocked 或实际失败；说明原因 |
| 同机多进程等于双物理机 LAN | 分别记录；物理环境缺失保持 NOT_VERIFIED |
| 构建通过等于 Unity/AOT 或完整可玩 | 构建只证明自己的目标范围 |
| 候选目录等于生产配置 | 候选保留候选身份 |
| 已有配置等于 CI/required check 已运行 | 核实实际运行与结果 |
| 性能延期等于达标 | 保留延期和未验证状态 |
| 文件存在或序列化成功等于掉电事务 | 单独声明故障模型与实际覆盖 |
| 文档写完就把 Proposed ADR 改 Accepted | 等待真实决定，不自行晋级 |

这些是模型和审阅规则，不能声称已安装成文件权限、CI 或运行时强制封锁。

## B 已确定产品与架构中的禁止行为

以下规则来自明确的产品决定或经授权补足的设计；细节来源在配套设计交接中按 A–H 主题索引。它们与“模型当前不得做哪些操作”分开。

### B1 Host、Client 与权威

- 不把 Host 自动认作存档 Owner。
- 不让房主本地玩家走旁路，获得远端玩家没有的写权限。
- 不让 Client、网络回调、Unity 表现或诊断直接提交权威玩法状态。
- 不在同一房间建立第二个业务 Tick 或第二份可写真相。
- 不把动画完成、渲染帧或墙钟作为加工成功依据。
- 不把 Socket 生命周期当作逻辑 Participant 或 Match 的生命周期。
- 不让旧连接、旧小关代际、旧会话继续提交有效命令。
- 不把传输 ACK、命令准入、业务提交、完整投影和 Ready 混为一件事。
- 不通过重连回滚 Host 当前世界，或把 Client 私有状态覆盖厨房、订单、装修和 Buff。
- 不让暂停期间继续推进烹饪、客流、伙伴或供应时钟。
- 不把一次断线、Host 关闭或异常终止伪装成小关失败或低星成功。

### B2 存档、分支与领取

- 不在准备、营业、半帧或半条命令执行时写产品成功检查点。
- 不用失败现场或成功前的中断覆盖最近成功检查点。
- 不把技术同步快照当作“随时自动保存”的产品授权。
- 不在检查点写入失败时继续公布下一小关。
- 不让新导入分支隐式写回原始 SaveSlot。
- 不自动合并存档，不按时间戳选赢家覆盖来源。
- 不把谱系 ID 当成覆盖授权。
- 不因小关成功就自动写所有人的本地文件。
- 不让本关开局资格名单之外的人领取本关结果。
- 不在领取写入失败时消耗资格，不让重复请求重复新建或覆盖。
- 不在显式覆盖时合并旧内容或改变目标存档 Owner。
- 不在覆盖成功后保留上一版本或用户可恢复备份；提交完成前必须保护旧记录。
- 不承诺无中心服务条件下跨设备的全局一次性领取或全局撤销。
- 不用尚未成功的小关生成可领取进度。
- 不让 PC 与 Android 互联或互换存档、授权包、结果及领取凭证。
- 不把绝对文件路径、文件句柄、Unity 对象或 ET 运行身份当作网络／存档业务身份。

### B3 大小关与评分

- 不把一个大关中的每个小关变成互不相干的新餐厅。
- 不因释放 Level 顺带销毁应延续的厨房物料、容器和加工。
- 不把活 Runtime、旧连接、旧待执行队列或同步水位搬到另一个 Match。
- 不因有准备操作就新增独立“关间准备”产品生命周期。
- 不在成功跨关时重复叠加标准供应或回满已消耗份数。
- 不把上一小关的订单、顾客、得分上下文和伙伴关内成长带成下一关的有效状态。
- 不设置正常营业的强制达标目标、失败条件或失败界面。
- 不给未满足订单倒扣分，不用 0 星阻止继续。
- 不让第一版星级决定装修、Buff、解锁或存档奖励。
- 不把早期“Buff 整个大关有效”解释成 Match 全局自动继承；当前 Level 声明其生效状态。
- 不以“解锁过”绕过本关允许集。
- 不为收尾成功强制销毁所有后厨成果，或要求搬尽所有在途货物。

### B4 NPC 与前厅体验

- 不把固定伙伴改成可反复招聘、替换、拼数值的普通员工系统。
- 不让玩家承担固定伙伴岗位安排、局内指派或复杂优先级微操。
- 不把伙伴能力成长默认延续到下一小关；稳定身份与长期陪伴另行保留。
- 不把玩家完成的工作计入伙伴成长。
- 不让未完成任务增加伙伴完成计数。
- 不在解锁加速时改变已经开始任务的冻结耗时。
- 不让一项工作同时被两位执行者完成或重复产生业务效果。
- 不把顾客等询问变成额外惩罚来源。
- 不拿桌号当稳定顾客或订单身份。
- 不给已经离席的顾客补开幽灵订单。
- 不把可选的人工前厅接手变成玩家必须逐桌服务的负担。
- 不把关间聊天默认变成数值奖励或成长触发。

伙伴工资、疲劳、心情、饥饿等维护槽未进入基础范围，不能因为“更真实”自行加入。它们没有被确认成永远不能讨论的机制。

### B5 物品、加工、订单与菜品

- 不让普通手槽或台面无条件放多个物件，不把普通台面变成无限背包。
- 不让同一物件同时出现在手里、桌上和容器中，不形成包含环。
- 不因搬走容器、换人接手或跨关丢失内容、进度或份数。
- 不让两人抢最后一份都成功，不让重复指令复制食物、扣料或结算。
- 不在操作拒绝时留下部分扣料、部分搬运或半份产物。
- 不让手工作业换人后重置进度，或靠同时两人操作默认加速。
- 不把端走已启动的汤锅改成停止煮制，也不允许取消该代表菜的既定自动煮制。
- 不在完成批次中继续加料、拿走锁定输入或重复启动。
- 不用旧 Pour 将多份完成批次整批输出；它有独立按份盛装动作。
- 不因清空内容顺带销毁锅、嵌套容器或设备，不隐式退料回库、给分或退款。
- 不把“制作完成”“放在台面”和“已交付订单”当作同一状态。
- 不让饮品跳过独立订单绑定；不强制所有餐食和甜品额外贴标签。
- 不在交付后解绑或换绑，不在新绑定失败时丢掉原有效绑定。
- 不跳过模具、烤盘、蒸篮、炸篮或指定出餐容器的实际约束。
- 不把熟饭、茶底、果汁等需要现场制备的材料凭空从供应点取出。
- 不把必须最后添加的奶泡、奶盖等提前混入以跳过阶段。
- 不把一份 ×2 投入归并成只投一份。
- 不混同供应番茄酱与现制热酱、速溶与现泡奶茶、半成品与盘装成品、蛋花汤与目录番茄汤。
- 不给黑糖珍珠鲜奶默认加入茶。
- 不按糖度、杯型、冰热组合重复扩充 87 款候选数量。
- 不把测试用价格、耗时、容量、产量或评分当成正式平衡。

### B6 供应、布局与本机联网工具

- 不把有限库存自动回满，不把所有来源当无限取料点。
- 不在请求采购后立即凭空增加厨房实物。
- 不用独立可消费库存数字重复表达已经存在的实物数量。
- 不在收货槽满时吞货，不重复接收同一货物。
- 不在收尾继续新申请供应；已经批准的货物仍按规则处理。
- 不在营业中搬设备或安装新布局。
- 不允许调用方缩小设备占地、伪造能力或权限以绕过布局校验。
- 不在布局失败时半搬完现场，或删除失去位置的食材和容器。
- 不用忽略角色半径的通路证明实际可达，不让顾客与玩家读取矛盾地形。
- 不在调用方另写端口选择逻辑；旧工具路径须先 GetPort，再以真实绑定／READY 为准。
- 不把候选端口当成租赁或保留，不静默选范围外端口。
- 不关闭防火墙，不自动修改网络类别或开放 TCP，不扩大其他程序规则。
- 不用 TCP 探测证明 UDP 连通，不把本机监听当作真实远端连通。

### B7 旧工程特有的架构边界

这些条款适用于原 AbilityKit/ET 工程，不把具体框架强制带到新项目。

- 不隐式升级固定 ET 副本，不把完整 ET 网络／调度栈当隐藏前置。
- 不把 package 版本混写为统一 ET 大版本。
- 不把玩法规则、房间产品流程和权威策略塞进通用框架。
- 不在迁移时保留旧可写权威，再增加第二个 writer。
- 不用 ET Parent 代替业务关联；不能靠 reparent 表达加工换工位。
- 不让 DI 与 ET 两方重复负责释放同一资源。
- 不在重构中悄悄把已提交命令保留的事务语义改成整帧回滚。
- 不让日志、观测、通知成功与否驱动业务成功或回滚。
- 不手改生成文件，不让 Check 修改输入或产物。
- 不使用浮动 latest/main 依赖，不以名字或 IsPackable=false 推断可再分发。
- 不编辑 Unity 自动生成 csproj、Library、Temp，不删除 Editor 锁文件。

## C 暂缓、未决与来源冲突

### C1 当前未授权，不写成永久禁止

| 事项 | 已有边界 | 未来讨论的入口 |
|---|---|---|
| Cooking Unity | 旧工程长期禁止实施，原独立门未解除 | Owner 明确重新立项；新项目引擎另选 |
| 主机迁移、公网、中继、NAT、大厅、观战、多房间 | 未进入已批准基础范围 | 新需求与技术选择 |
| 预测、回滚、严格 lockstep、Delta/Diff | 首阶段不做 | 测量和需求明确后单独讨论 |
| 火灾、故障、过熟、烧焦、保质、污渍 | 未进入基础玩法 | 明确产品行为后另定 |
| 投掷、接取、冲刺、任意落地堆积／堆叠 | 后置能力 | 单独决定操作和空间规则 |
| 精细切割、翻面、拉花、封口等小游戏 | 基础范围不加入 | 不因现实流程自行追加 |
| 复杂经济、采购取消、更多伙伴能力与特殊顾客 | 未定完整规则 | Owner 具体指定 |
| 正式价格、耗时、产量、人数、各关菜单 | 尚未平衡或确认 | 不用 fixture 数值填空 |
| 授权签名、密钥、撤销、中心服务与断电恢复 | 产品语义已有，完整协议未定 | 明确安全和故障模型后设计 |
| 新项目技术栈 | 未选定 | 不自动继承 ET、LiteNet 或旧测试框架 |

原网络路线不采用 TCP/KCP，是后来明确的旧项目选择；新项目需要重新选型。不得把旧计划中未授权的内容作为“已经答应实现”。

### C2 有冲突，不补造单一禁令

| 事项 | 来源中的差异 | 本次整理结论 |
|---|---|---|
| 暂停待执行命令 | 早期明确确认取消；生命周期参考要求保留；后续网络设计要求终结 | 交接差异，新项目须明确选择 |
| 断线手持物 | 早期明确确认落到合法世界位置；后续网络设计要求不自动转移 | 没找到 Owner 后续改约原话，不能助手代定 |
| 结束时 NPC 任务 | 旧自动路径按完成效果收口；新人工前厅路径自然排空 | 按适用模式区分，不写“全部瞬间完成” |
| 下一关禁用旧菜 | 后续设计允许保留旧存量和已受理工作，但禁止新制作等操作 | 不扩大成“必须删光”或“继续无限新做” |

禁止项清单不能靠简化消灭这些差异。具体设计取舍见配套交接 H2。

## D 交给下一项目的使用方式与来源

### D1 如何使用

- A 节保留当前模型行动禁令；不能用交接请求恢复旧工程。
- B 节保存原产品共识；调整产品规则需要明确决定。
- C 节保留暂缓和未决，不自动扩成永久禁令。
- 旧仓库专用路径、版本、依赖和工作流不自动成为新项目要求。
- 新项目若要把条款写入自己的 AGENTS，由 Owner 选择适用项；本文没有安装任何机器强制规则。
- “没有禁止”不代表“已授权实施”；同样不能凭禁令清单要求无关审批、扩大门禁或制造更多证据。
